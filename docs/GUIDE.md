# FunPay BOT — подробное руководство

[← На главную страницу проекта](../README.md)

Версия: **v1.25**.

FunPay BOT помогает управлять аккаунтом FunPay из Telegram-супергруппы с темами: перепиской, заказами, лотами, автоматическими сообщениями и финансами. Ядро разделено на модули пакета `funpay_bot`, а плагины используют общий `unified_sdk` и добавляют правила конкретного товара и работу с поставщиком.

## Возможности

| Раздел | Что умеет бот |
| --- | --- |
| Чаты FunPay | Создаёт темы покупателей, передаёт новые сообщения, изображения, системные сообщения и обращения поддержки; позволяет отвечать из Telegram |
| Заказы | Ведёт хронологию и общую карточку заказа со статусом, прогрессом и отзывом; предоставляет действия выполнения и возврата |
| Автоматизация | Приветствия, заготовки ответов, ответы по командам, сообщение после подтверждения, напоминания о подтверждении и отзыве, ответы на отзывы |
| Автотикеты | Формирует списки неподтверждённых заказов; по словарю выявляет признаки претензий и запрашивает решение владельца; соблюдает интервал 24 часа |
| Лоты | Обнаруживает свои лоты, управляет активностью и остатками, рассчитывает защитную цену и корректирует цену относительно конкурентов; общий воркер поддерживает `common` и `chips` |
| Финансы | Учитывает выручку, себестоимость, возвраты и прямые закупки; показывает доступность вывода, учитывает задержку и комиссии |
| Вывод средств | Предварительный расчёт и подтверждение ручного вывода; отдельная настройка автовывода; уведомление о доступном балансе с кнопкой перехода в меню |
| Аккаунт | Статус продавца, онлайн/офлайн, автоподнятие лотов, профиль, курсы и общий еженедельный отчёт |
| Управление | Подключение и остановка плагинов, отдельные прокси Telegram/FunPay, смена `golden_key`, перезапуск, журналы и ручные ZIP-копии |
| Расширения | Общие карточки, настройки, состояние, маршрутизация кнопок, очередь, таймеры и задачи; для товарных интеграций — общая машина заказов и учёт |

В публичной поставке один плагин — **Инструменты лотов** (`lot_tools.py`): экспорт, импорт и очистка обычных лотов через интерфейс ядра. Автоматизация, отладчик и демпер входят в ядро.

Фреймворк также позволяет самостоятельно создавать товарные интеграции. Их контракты и примеры описаны в разделе «Свой плагин»; готовые интеграции поставщиков в публичный релиз не входят.

## Быстрый старт

Создайте Telegram-бота через @BotFather, добавьте его администратором в супергруппу с темами и распакуйте релиз.

**Linux** — из папки проекта:

```bash
bash start.sh
```

**Windows** — запустите `start.bat`.

Первый запуск создаёт окружение и запрашивает токен Telegram, `group_id`, `owner_id`, `golden_key` и User-Agent FunPay. После настройки отправьте `/menu` в своей группе. Инструменты лотов доступны через меню; подключение собственных расширений описано ниже.

## Установка и первый запуск

### Подготовка

1. Установите Python; требования к версии и полный список пакетов приведены в [последнем разделе](#зависимости).
2. Распакуйте релиз и откройте папку `FunPayBOT`, где находится `main.py`.
3. Создайте Telegram-бота через [@BotFather](https://t.me/BotFather) и сохраните его токен.
4. Создайте супергруппу, включите темы и добавьте бота администратором. Выдайте права управления темами, закрепления и удаления сообщений.
5. Подготовьте полный ID группы, ID владельца и данные сессии FunPay. Они описаны в [настройке](#настройка).

### Linux

Из папки проекта:

```bash
bash start.sh
```

Скрипт создаёт `.venv` и запускает бот. Для повторного открытия установщика:

```bash
bash install.sh
```

При необходимости можно выбрать установленный интерпретатор:

```bash
PYTHON_BIN=python3.12 bash start.sh
```

В системе должен быть доступен модуль `venv`; в Debian/Ubuntu он поставляется пакетом `python3-venv` или пакетом для выбранной версии Python.

### Windows

Установите Python с launcher `py`, затем запустите `start.bat`. Скрипт предпочитает Python 3.12, иначе использует доступный `py -3`. Для повторной настройки запустите `install.bat`.

### Что происходит при запуске

Пакеты и настройки обрабатываются отдельно. При отсутствующих или несовпадающих зависимостях стартовый механизм устанавливает закреплённые версии и перезапускает процесс. Корректные конфиги сохраняются. Если обязательных настроек нет или они неверны, открывается установщик с запросом конкретных полей. Повреждённый JSON не перезаписывается пустым файлом: исправьте указанный файл и запустите бот снова.

После запуска отправьте `/menu` в настроенной группе. Откройте инструменты через меню. Менеджеры лотов находятся в главном разделе «Лоты»; раздел «Плагины» управляет установленными расширениями.

Дополнительные варианты запуска из подготовленного окружения:

```bash
.venv/bin/python main.py --run
.venv/bin/python main.py --install
```

На Windows используйте `.venv\Scripts\python.exe` вместо `.venv/bin/python`. Аргумент `--config /путь/config.json` задаёт другой корневой конфиг; рабочие файлы располагаются относительно его папки.

Для обновления остановите процесс, замените исходники и `vendor` из релиза, сохранив свои `config.json`, конфиги плагинов и папку `data`, затем запустите бот. Финальная сборка использует текущие JSON напрямую. Автоматический импорт INI, bootstrap/profile-архивов и исходных плагинов Cardinal отсутствует. Не удаляйте `data/state.json` ради сброса настройки: файл содержит историю и следы денежных операций.

## Доступ и команды

Бот работает только в супергруппе из `telegram.group_id`. В личке и других группах он не отвечает. Для доступа используются два параметра:

- `owner_id` — положительный ID пользователя-владельца;
- `group_id` — полный отрицательный ID супергруппы вида `-100…`.

`admin_ids` не используется. Принимаются сообщения владельца и сообщения от имени самой настроенной группы — например, от анонимного администратора через `sender_chat`. Telegram не раскрывает личность такого отправителя; ввод от имени группы использует общую сессию с владельцем. Кнопки обрабатываются только для реального владельца.

Команды регистрируются для всей настроенной группы через `BotCommandScopeChat`. Видимость команды в списке не даёт права управлять ботом.

| Команда | Назначение |
| --- | --- |
| `/menu` | Главное меню |
| `/backup` | Выгрузка и загрузка ZIP-копии |
| `/proxy` | Раздельные настройки прокси Telegram и FunPay |
| `/golden_key` | Смена ключа сессии FunPay |
| `/restart` | Подтверждение перезапуска процесса бота |
| `/debug` | Переключение встроенного режима отладки |
| `/lot_tools` | Открытие инструментов лотов |

Команды систем добавляются и убираются при их подключении и остановке. `/restart` сохраняет состояние и завершает рабочие ресурсы перед перезапуском процесса.

## Настройка

Все файлы настроек называются `config.json`. Разделы и имена служебных ключей сохраняются в lowercase. Содержимое команд, ID и пользовательских шаблонов не приводится принудительно к другому регистру. Штатные меню сохраняют изменения сами; вручную редактируйте JSON при остановленном боте.

### Обязательные данные Telegram и FunPay

| Параметр | Что указать и где получить |
| --- | --- |
| `telegram.token` | Токен своего бота из @BotFather; шаблон `YOUR-BOT-TOKEN` |
| `telegram.group_id` | Полный ID вашей супергруппы с темами; шаблон `YOUR-GROUP-ID` |
| `telegram.owner_id` | Числовой ID Telegram-пользователя, который управляет ботом; шаблон `YOUR-OWNER-ID` |
| `funpay.golden_key` | Значение cookie `golden_key` авторизованного аккаунта FunPay; шаблон `YOUR-GOLDEN-KEY` |
| `funpay.user_agent` | User-Agent браузерной сессии FunPay; шаблон `YOUR-USER-AGENT` |

ID пользователя берётся из поля `from.id`, группы — из `chat.id` Telegram Bot API. В ссылке вида `https://t.me/c/GROUP-NUMBER/MESSAGE-ID` часть `GROUP-NUMBER` соответствует группе: добавьте перед ней `-100`, чтобы получить полный ID супергруппы. `MESSAGE-ID` — номер сообщения, он не нужен в `group_id`.

Для получения `golden_key` войдите в свой аккаунт на `funpay.com`, откройте инструменты разработчика браузера → Application/Storage → Cookies → FunPay и скопируйте **значение** cookie `golden_key`. User-Agent можно посмотреть в заголовках запроса браузера или через `navigator.userAgent` в консоли этой же сессии.

Минимальный фрагмент корневого конфига:

```json
{
  "telegram": {
    "token": "YOUR-BOT-TOKEN",
    "group_id": "YOUR-GROUP-ID",
    "owner_id": "YOUR-OWNER-ID",
    "proxy": ""
  },
  "funpay": {
    "golden_key": "YOUR-GOLDEN-KEY",
    "user_agent": "YOUR-USER-AGENT",
    "proxy": "",
    "poll_seconds": 6
  },
  "plugins": {
    "enabled": "auto"
  }
}
```

Это шаблон: замените `YOUR-…` своими значениями, ID — корректными числовыми идентификаторами. Остальные отсутствующие параметры получают встроенные значения по умолчанию.

Рабочие токены, cookies, `golden_key`, мнемонику, ключи поставщиков, конфиги, `data` и резервные ZIP не публикуйте в репозитории. Примеры в этом README содержат только заглушки.

### Прокси и смена сессии

`telegram.proxy` и `funpay.proxy` независимы. Допустимы `http://`, `https://`, `socks5://`, при необходимости с логином и паролем, например `socks5://LOGIN:PASSWORD@HOST:PORT`. Пустая строка отключает прокси.

Команда `/proxy` открывает два направления настройки. Изменения применяются после перезапуска. `/golden_key` принимает новый ключ и удаляет сообщение с ним; затем требуется перезапуск для применения новой сессии.

### Формат правил и шаблонов

`autogreetings.lot_greetings` — объект «шаблон полного описания лота → текст». `{}` в шаблоне соответствует переменному фрагменту.

`autoresponse.commands` — объект «команда → правило». Правило содержит `enabled`, `response`, `notify`, `trigger_author` со значением `BUYER`. Глобального enabled для этого блока нет; включение задаётся по каждой команде. `notify` управляет уведомлением о срабатывании. `notification_text` применяется к уведомлению с подстановкой `{username}` и `{command}`.

`reviewreply` имеет ключи `1`…`5`, `reviewchatreply` — `1`…`6`; значение каждого ключа — объект `enable`, `text`. 6 соответствует отсутствующему отзыву в событиях, где поддерживается реакция на его удаление. Расписания и служебные отметки обработанных заказов находятся в state, а не в конфиге.

У `autoticket.message` используйте два заполнителя: `{clear_orders}` и `{ambiguous_orders}`. Указывать постоянное «Нет» во втором списке не следует: это скроет фактические спорные заказы.

`chattemplates.items` — объект стабильный ID → title, text, enabled. Пользовательские тексты в defaults отсутствуют. Заготовки видны в закрепах тем покупателей.

## Работа с ботом

### Главное меню, системы и темы

Главное меню объединяет автоматизацию, лоты, плагины, профиль, статус системы, финансы, курсы, отчёты, уведомления и логи.

В разделе **«Плагины»** открываются интерфейсы систем и находятся кнопки их запуска/остановки. Остановка отменяет задачи и сохраняет незавершённые операции, но не закрывает тему: систему можно включить снова. **«Выдача»** переключается в меню самого товарного плагина. Пауза новых заказов не означает повторную оплату уже начатых операций.

Все **менеджеры лотов** открываются из главного раздела «Лоты»; кнопки конкретной системы расположены в два столбца. В меню плагинов эти менеджеры не дублируются.

Для известных боту тем используются значки: 🤖 главная, 📝 инструменты, 🛍 заказы, 💬 покупатели. Поддержка выделяется ❗ и отметкой ‼️ в названии. Посторонние темы группы не присваиваются боту.

### Переписка и заказы

На первой синхронизации старую переписку бот в темы не выгружает. Дальнейшие сообщения попадают в тему соответствующего покупателя. Отображаются также системные сообщения FunPay и сообщения поддержки: системный отправитель отмечается 🔵, поддержка — 🆘. Изменения статуса заказа остаются в хронологии и общей карточке заказа.

Из Telegram можно отправлять текст и изображения, включая фотографии и графические файлы PNG/JPEG/WebP. Заготовки ответов доступны в закрепах тем покупателей. Вотермарка применяется к автоматическим сообщениям и заготовкам, если включена; обычная ручная переписка и изображения отправляются без неё.

Товарная интеграция связывает оплаченный заказ, получателя и подтверждение покупателя. До внешнего платежа сохраняется намерение операции. Если результат отправки неизвестен, система переходит к сверке, а не к повторной закупке. Чек, ссылка на транзакцию или подтверждённый ID поставщика сопровождает результат. Прямая закупка из меню требует подтверждения суммы; после неё указывается выручка либо выбирается «Покупка себе», чтобы отделить её от продаж FunPay.

### Автоматизация сообщений

- **Приветствия:** общий текст и варианты по шаблонам полного описания лота; `{}` обозначает переменный фрагмент. Пауза действует на чат; можно ограничить приветствия новыми чатами.
- **Автоответы:** точное совпадение команды без учёта регистра, собственные текст и флаг уведомления для каждого правила. В правиле используется `trigger_author: "BUYER"`.
- **Ответ после подтверждения:** отдельный текст благодарности покупателю.
- **Напоминание о подтверждении:** планируется после явной отметки выполнения оплаченного заказа.
- **Напоминание об отзыве:** после выполнения и подтверждения заказа. Возврат или полученный отзыв отменяет соответствующее напоминание.
- **Ответы на отзывы:** публичный ответ для оценок 1–5 и отдельное сообщение в чат; в чат-правилах ключ `6` относится к отсутствующему/удалённому отзыву, реакция на изменение включается отдельно.
- **Вотермарка:** управляемая подпись автоматических сообщений.

Подстановки текстов: `$username` / `{username}`, `$order_id` / `{order_id}`, `$date` / `{date}`, `$time` / `{time}`; для автоответа также `{command}`.

Пример правила автоответа:

```json
{
  "autoresponse": {
    "commands": {
      "!help": {
        "enabled": true,
        "response": "Здравствуйте, {username}! Напишите ваш вопрос.",
        "notify": true,
        "trigger_author": "BUYER"
      }
    },
    "notification_text": "Покупатель {username} вызвал команду {command}."
  }
}
```

### Автотикеты

Внешняя нейросеть не используется. Словарные признаки претензий — например, «не работает», «не могу зайти», «не пришло», «не туда отправил», «ошибка» и близкие формулировки — отправляют заказ на ручное решение владельца. Неполная доступная история также требует ручного решения. Для проблемного заказа можно выбрать однозначный список, спорный список или пропуск; остальные подходящие оплаченные заказы обрабатываются автоматически.

Шаблон сохраняет два разных списка:

```text
1) {clear_orders}

2) {ambiguous_orders}
```

В первом должны быть случаи, когда услуга оказана и покупатель явно забыл подтвердить заказ. Во втором — неоднозначные ситуации и претензии. Отсутствие найденных слов само по себе не доказывает оказание услуги: алгоритм выполняет словарную фильтрацию переписки. Не заменяйте `{ambiguous_orders}` постоянным текстом «Нет».

Между попытками отправки тикета выдерживается минимум **24 часа для всей отправки**, в том числе после перезапуска и при неизвестном исходе запроса. Изменение времени запуска это ограничение не сокращает. По умолчанию автотикеты выключены.

### Лоты и общий демпер

Главное меню → «Лоты» → система: обнаружение своих лотов, активность, категория, защитная цена, целевая прибыль, остатки, профиль и параметры демпера. Общий сервис `CoreLotDumper` — внутренний воркер ядра; у него нет отдельного плагина или независимого меню. Торговый runtime вызывает его по настройкам своей системы, обычно примерно раз в 1500 секунд и при изменении расчётных данных.

Поддерживаются обычные лоты `common` и предложения `chips`. Для `chips` учитываются категория, сервер и сторона. Расчёт учитывает себестоимость, прибыль, долю выплаты и комиссию категории. Вручную выключенный лот не включается только из-за пересчёта цены. Подробный контракт профиля для разработчиков приведён ниже.

«Инструменты лотов» экспортируют и импортируют обычные лоты в формате `unified-lots-v1`, с изображениями в пределах лимита. Доступны до 1000 лотов и до 30 МБ изображений; включение содержимого склада задаётся отдельно. Импортируемые лоты создаются выключенными и с `auto_delivery=false`. Очистка требует подтверждения владельца. Поддержка `chips` общим демпером не означает поддержку переноса `chips` этим инструментом.

### Финансы, задержка и вывод

Единый журнал объединяет выручку, себестоимость, возвраты, прямые закупки и выводы. Доступный к выводу баланс определяется по данным FunPay. Дополнительный локальный учёт задержки **48 часов** после подтверждения заказа включается через `finance.hold_enabled`; его можно отключить. Это не отменяет собственные ограничения площадки. Поле `hold_hours` в текущей версии не следует использовать для задания произвольного срока: рабочая политика — 48 часов.

| Способ | Ориентир комиссии | Порог уведомления |
| --- | --- | --- |
| Карта / СБП | 3%, минимум 30 ₽ | 1000 ₽ |
| USDT TRC20 | 6%, минимум 150 ₽ | 2500 ₽ |

Пороги нужны для учёта минимальной комиссии. Уведомление появляется, когда средства доступны и достигнут расчётный порог. Его кнопка **открывает меню вывода**. Уведомления отключаются отдельно через `finance.withdraw_notifications` и настройки уведомлений. Фактическая сумма и комиссия берутся из предложения FunPay при предварительном расчёте; для криптовывода отдельно учитывается курсовая разница.

В ручном выводе выбираются способ, реквизиты, сумма или весь доступный остаток с учётом резерва, затем подтверждается расчёт. Автовывод — отдельная функция `autowithdraw.enabled`, изначально выключенная. Для неё нужны `method`, `method_kind`, `wallet`, `minimum`, `reserve` и интервал. Неизвестный результат денежной операции требует сверки и не повторяется автоматически.

### Курсы, отчёт, уведомления и журналы

Курсы USDT/RUB и TON/USD используются в общих карточках. Еженедельный отчёт собирает общую статистику и график; плагины передают данные в него, вместо создания отдельных одинаковых отчётов. Время задаётся в `weeklyreport`, часовой пояс — в `general.timezone`.

Раздел `notifications` отдельно управляет автоответами, новыми заказами, статусами, отзывами, событиями лотов, выдачей, тикетами, выводами и автоподнятием. Журналы доступны через «Логи»; основной файл — `data/log.log`, размер и ротация задаются в `logging`.

### Резервные копии

`/backup` открывает выгрузку и загрузку ZIP. Копия создаётся только по запросу и включает корневой конфиг, конфиги плагинов, `data/state.json` и манифест SHA256. Фонового резервирования нет; выгруженный ZIP автоматически не складируется на диске.

Восстановление принимает полный архив `unified-backup-v2` размером до 40 МБ. Копия привязана к боту, группе и аккаунту; устаревшее состояние с потерей следов оплаченных операций не применяется. После подтверждения архив помещается в `data/restore-pending.zip` и применяется при следующем запуске до сетевой работы. Резервная копия содержит доступы: храните её приватно.

## Свой плагин

### Границы ядра и расширений

Фреймворк находится в `funpay_bot/framework.py` и `funpay_bot/commerce.py`; публичный интерфейс экспортируется через `unified_sdk.py`. Устанавливать отдельный пакет `unified_sdk` через pip не нужно. В ядре находятся Telegram-транспорт, доступ, темы, маршрутизация, очередь событий, автоматизация, финансы, состояние и менеджер лотов. В плагине остаются только собственная функциональность, API поставщика и правила товара.

`FrameworkPlugin` подходит для любого расширения. `CommercePlugin` добавляет общую машину заказов, настройки, закупку, учёт, интерфейс и профиль лотов. API поставщика и правила товара реализуются в конкретном расширении; универсальные механизмы ядра не должны ветвиться по его названию.

### Минимальный плагин

Создайте `plugins/example.py`. ID берётся из имени файла, соответствует `[a-z][a-z0-9_]{0,23}` и остаётся постоянным: к нему привязаны конфиг, тема и состояние. При `plugins.enabled="auto"` корректные файлы обнаруживаются автоматически; файлы с начальным `_` пропускаются. Не кладите незаконченные примеры в рабочую папку плагинов.

Обязательны `API_VERSION = 1`, `NAME` и класс `Plugin(ctx)`. `VERSION` импортируется из SDK.

```python
from unified_sdk import FrameworkPlugin, VERSION

API_VERSION = 1
NAME = "📝 Example"
TOPIC_ICON = "📝"


class Plugin(FrameworkPlugin):
    def __init__(self, ctx):
        super().__init__(ctx)
        self.runtime.router.on("menu", lambda action, user: self.menu())

    async def start(self):
        await super().start()
        await self.menu()

    async def menu(self, *, new_message=False):
        await self.ctx.card(
            "Пример плагина FunPay BOT",
            [[("Обновить", "menu")]],
            new_message=new_message,
        )
```

После запуска плагин создаёт карточку в своей теме. `ctx.card` добавляет ID к локальному действию: `menu` становится `example:menu`. В обработчик приходит локальная часть; авторизация, тема и актуальность карточки контролируются хостом. Формат `p:example:menu` не используется.

`TOPIC_ICON` задаёт подходящий эмодзи для доступного значка темы Telegram. `TOPIC=False` отключает создание отдельной темы; тогда интерфейс нужно предоставлять через возможности ядра, поскольку `ctx.card/say/file` рассчитаны на тему плагина.

### Runtime

| Механизм | Использование |
| --- | --- |
| `runtime.register(name, component)` | Компонент экземпляра; дубликат имени запрещён |
| `runtime.provide(name, service)` | Возможность, которую может вызвать ядро |
| `runtime.on(event, handler)` | Обработчики start, stop, event, tick, message |
| `runtime.router.on(action, handler)` | Точное действие; handler получает action, user |
| `runtime.router.on_prefix(prefix, handler)` | Маршрут по префиксу; более длинный имеет приоритет |
| `runtime.start_worker(name, worker)` | Задача без дублирующего запуска с тем же именем |
| `runtime.queue.submit(operation)` | Последовательная async-операция |
| `runtime.timers.schedule(key, delay, callback)` | Заменяемый RAM-таймер |
| `runtime.generation.advance()` / `current(token)` | Проверка актуальности после ожидания |

Повторный start не запускает lifecycle дважды. stop отменяет задачи/таймеры, закрывает очередь и меняет поколение. Если переопределяете start/stop, вызывайте `super()`. Для товарных расширений используйте `configure_runtime()` вместо дублирования стандартного lifecycle.

RAM-таймеры не сохраняются при перезапуске. Долгоживущие задания хранятся с phase/due/reference в состоянии. RetryPolicy предназначен для безопасных ошибок до оплаты; неизвестный денежный POST повторять нельзя.

### Контекст

| Метод | Назначение |
| --- | --- |
| `ctx.config_store(defaults)` | JSON-конфиг плагина |
| `ctx.state`, `ctx.save_state()` | Состояние экземпляра и его сохранение |
| `ctx.card`, `ctx.say`, `ctx.file` | Карточка, сообщение, файл в теме плагина |
| `ctx.send_buyer(event, text, action_id)` | Отправка покупателю с именованным ключом действия |
| `ctx.claim_order(event)` | Захват оплаченного заказа |
| `ctx.order_progress(event, phase, description)` | Прогресс общей карточки заказа |
| `ctx.fulfilled(event)` | Отметка фактического выполнения |
| `ctx.publish_rates(text)`, `ctx.publish_report(text)` | Данные для общего блока курсов/отчёта |
| `ctx.app.notify(kind, text, rows)` | Уведомление с учётом настройки типа |

Плагин — доверенный Python-код с правами процесса, не песочница. Не помещайте requests в event loop: используйте `asyncio.to_thread` или async-клиент. Импорт плагина должен только объявлять классы/метаданные: никаких сетевых закупок, запуска потоков или установки pip.

### Товарный плагин

```python
from unified_sdk import CommercePlugin, ProviderAdapter, ProductAdapter, VERSION

API_VERSION = 1
NAME = '📝 Example'
TOPIC_ICON = '📝'

class Provider(ProviderAdapter):
    REQUIRED_FIELDS = ('api_key',)
    # Реализуйте provider_balance, provider_prepare,
    # provider_pay, provider_status и доказательство операции.

class Product(ProductAdapter):
    QUANTITY_PATTERNS = (r'(\d+) units',)
    CATALOG_COMMANDS = ('!units',)
    # Реализуйте normalize_recipient, valid_quantity, buyer_receipt.

class Plugin(CommercePlugin):
    PROVIDER = Provider
    PRODUCT = Product
    CATEGORY_ID = 1
    TITLE = NAME
    PRODUCT_LABEL = 'units'
    RECIPIENT_PROMPT = 'идентификатор получателя'
    DEFAULTS = {'api_key': 'YOUR-API-KEY'}
    INSTALL_FIELDS = {'api_key': ('Ключ поставщика', True)}
```

Это схема контракта, а не готовая интеграция: незаполненные адаптеры нельзя включать для реальных заказов.

`CommercePlugin` автоматически связывает provider/product, стандартные hooks, интерфейс, учёт и `lot_profile`. Объекты независимы у разных экземпляров. Плагин объявляет только собственные SETTINGS_SCHEMA; общие настройки категории, возврата, прибыли, выдачи, выплаты и демпера добавляет базовый класс. Схема глубоко копируется для экземпляра.

#### ProviderAdapter

- `REQUIRED_FIELDS` — обязательные ключи Provider.
- `FIELD_VALIDATORS` — словарь `поле: callable(value)`; при неверном значении callable выбрасывает ValueError/TypeError. Используется и установщиком, и проверкой текущих реквизитов.
- `provider_balance()` — Decimal-совместимый доступный баланс поставщика в USDT.
- `provider_prepare(order)` — получает предложение и записывает `spent_usdt`, необходимые данные и идентификаторы; реальные средства не отправляет.
- `provider_pay(order)` — один платёж. Сохраните точный reference до сетевой отправки, если протокол позволяет подготовить его заранее; вызывайте `self.save()` после записи. Ядро уже сохранило payment_intent.
- `provider_status(order)` — `done` только при подтверждении доставки; `paid` означает оплату без доказательства выдачи, `failed` — ошибку с необходимостью сверки. Другой статус оставляет проверку активной.
- `receipt_url(order)` — ссылка на чек/транзакцию либо None.
- `operation_reference(order)` — ID для сообщений владельцу.
- `extra_operation_cost()` — дополнительные расходы в рублях, по умолчанию 0.

Специфические HTTP-клиенты, токены, подписи и разрешённые адреса находятся в плагине. При изменении доступов сбрасывайте соответствующие сессионные токены. Нельзя переводить заказ с payment_intent обратно в ready или повторять оплату после тайм-аута.

#### ProductAdapter

`normalize_recipient(text)` возвращает нормализованного получателя либо None. `valid_quantity(quantity)` проверяет номинал. `paid_units(quantity)` по умолчанию возвращает количество; бонусные единицы учитываются переопределением в товаре.

`QUANTITY_PATTERNS` — регулярные выражения с количеством в первой группе. Общий парсер проверяет valid_quantity. `RECIPIENT_PATTERN` дополнительно извлекает кандидатов из описания; структурированные recipient/player/params/buyer_params обрабатываются общим механизмом.

`CATALOG_COMMANDS` включает ответы со списком лотов. `HELP_COMMANDS` задаёт словарь команда → текст. Для специфического поведения можно переопределить buyer_command. `buyer_receipt(order)` обязан содержать понятный результат и доказательство: подтверждённый ID операции либо ссылку на чек.

#### Настройки

Один элемент SETTINGS_SCHEMA содержит title, description, fields и необязательные section (`Plugin` по умолчанию), kind (`text`, `number`, `integer`, `bool`), minimum/maximum, choices, secret, validator. Несколько fields вводятся JSON-объектом с точным набором ключей. Значение проверяется до изменения конфига. INSTALL_FIELDS хранит подпись и признак секрета для консольного установщика.

#### Дополнительные компоненты

В `configure_runtime()` регистрируйте только особые сервисы, hooks или workers. Универсальное поведение добавляйте в ядро один раз; не копируйте стандартный интерфейс, учёт и машину заказов в каждый плагин. Обычные изменения лотов выполняются через общий менеджер и LotProfile, см. [профиль лотов](#профиль-лотов-и-вызов-воркера).

### Профиль лотов и вызов воркера

```python
from unified_sdk import LotProfile

profile = LotProfile(
    owner='example', category_id=99, kind='common',
    lots={
        '123': 50,
        '1-2-99-3-4': {
            'kind': 'chips', 'category': 99, 'quantity': 50,
            'keywords': 'сервер|сторона', 'minimum': '80',
            'step': '0.5', 'seller_tick': '0.0001',
        },
    },
    parse_quantity=lambda text: None,
)
```

Числа здесь — синтетический пример. Подставьте реальные ID и корректный парсер. Обычный ID состоит из цифр; chips использует полный ID предложения, его третья часть должна совпадать с категорией. Один профиль может содержать оба типа через явные дескрипторы. Количество должно быть положительным и допустимым для товара.

`CommercePlugin.lot_profile()` строит профиль из `plugin.category_id`, необязательного `lot_kind` (`common` по умолчанию) и `managed_lots`. Если товару нужен другой источник профиля, переопределите этот метод. Общую обработку копировать не нужно.

#### Настройки записи

`kind`, `category`, `quantity` определяют объект. Дополнительные параметры: `enabled`, `minimum`, `maximum`, `step`, `tick`, `seller_tick`, `keywords` с разделителем `|`, `minimum_rating`, `ignore_offline`, `excluded_sellers`, `only_sellers`, `currency`, `match_quantity`. `minimum` задаёт нижнюю границу цены продавца. `tick` относится к шагу сравниваемой цены; `seller_tick` — к точности итоговой цены продавца.

По умолчанию минимальный рейтинг 3, офлайн-продавцы игнорируются. Для common учитывается номинал по парсеру. Для chips дополнительно совпадают сервер/сторона из полного ID, чтобы не сравнивать разные предложения. Собственные лоты, неподходящая валюта и предложения ниже защитной границы исключаются.

Защитная цена продавца:

`(paid_units × unit_cost_usdt × purchase_rate_rub + extra_cost_rub + quantity × target_profit_per_unit) / effective_payout_rate`.

Она округляется вверх по точности продавца. Дополнительно учитывается коэффициент комиссии категории для сравнения публичных цен. При неизвестной комиссии или недопустимом максимуме обновление отклоняется. Демпер изменяет цену без включения вручную выключенного лота.

#### Вызов

Товарному плагину обычно достаточно унаследованного `manage_lots(action)`. Для собственной интеграции доступен `await app.lot_dumper.reprice(profile, floor_for, floor_only=False)`. `floor_for(spec)` — синхронная функция, возвращающая положительный Decimal-совместимый минимум для ManagedLot. Результат содержит checked, changed, errors.

`floor_only=True` поднимает только недостаточную цену без запроса конкурентов и не снижает цену. Обработка каждой записи изолирована; ошибка одной записи не блокирует остальные. Изменение common сериализуется по ID, chips — по категории. В офлайне записи на FunPay не выполняются.

### Состояние и жизненный цикл

`ctx.config_store(defaults)` создаёт хранилище настроек в `plugins/<id>/config.json`; объект имеет `.data` для доступа к разделам и `.save()` для сохранения. `ctx.state` — узел плагина в общем `data/state.json`; после изменения вызывайте `ctx.save_state()`. Токены и реквизиты относятся к конфигу, меняющиеся операции и сроки — к состоянию.

Запись JSON атомарная. `ctx.app.state.transaction()` предназначен для синхронного изменения состояния с откатом при ошибке; не выполняйте внутри сетевые `await`. RAM-таймеры не переживают перезапуск: сроки, фазы и reference долгих заданий нужно сохранять в состоянии.

Стандартный товарный сценарий: получатель → подтверждение → готовность → подготовка → оплата → подтверждение доставки → завершение. Ошибка до оплаты может ожидать безопасного повтора. После сохранённого `payment_intent` допустимы сверка или ручное решение; возврат в готовность с повторной оплатой недопустим. Известная reference после рестарта используется для получения статуса, а отсутствие reference требует ручного решения.

Отправляйте сообщения покупателю через `ctx.send_buyer(event, text, action_id)` со стабильным ключом действия. Фактическое выполнение отмечается `ctx.fulfilled(event)` и связывает интеграцию с общими напоминаниями и карточкой заказа. Для уведомлений с пользовательскими переключателями используйте `ctx.app.notify(kind, text, rows)`; `ctx.notify_main(text)` отправляет текст напрямую и не является заменой управляемым уведомлениям.

При переопределении `start`/`stop` вызывайте базовую реализацию. Дополнительные задачи запускайте через `runtime.start_worker`, чтобы остановка системы завершала их. Не создавайте отдельный Telegram-клиент, одинаковые меню, финансовый журнал или планировщик демпера в каждом плагине.

### Перенос плагина из FunPayCardinal

Исходный плагин Cardinal не совместим с FunPay BOT без адаптации. Автоматического конвертера нет.

| В Cardinal | В FunPay BOT |
| --- | --- |
| Глобальный объект Cardinal, `BIND_TO_*` | Экземпляр `Plugin(ctx)`, hooks runtime |
| `cardinal`, `telebot`, `tg_bot` | `unified_sdk` и общий Telegram-транспорт |
| Собственная одинаковая машина заказов | `CommercePlugin`, `ProviderAdapter`, `ProductAdapter` |
| Глобальные обработчики кнопок и собственные темы | `ctx.card` и локальные действия |
| Callback из отображаемого названия | Стабильный lowercase ID из имени файла |
| Свой демпер и менеджер лотов | `LotProfile` и общий воркер ядра |
| Дублирование настроек и учёта | Общая схема плюс поля конкретной интеграции |

Сначала выделите специфичные API-запросы, подписи, правила номинала, получателя и доказательства доставки. Объявите адаптеры и метаданные, перенесите настройки в JSON плагина, изменяемые данные — в его узел состояния. Интерфейс и общие действия подключайте через контекст и runtime. Для нового плагина не требуется добавлять его имя в ветвления ядра: он обнаруживается по файлу и объявляет возможности через `runtime.provide`.

Плагин является доверенным Python-кодом с правами процесса. Не размещайте в импорте сетевые операции, установку пакетов и запуск задач. Используйте async-клиент или `asyncio.to_thread` для блокирующих запросов. Персональные данные не должны попадать в исходники и публичные defaults.
